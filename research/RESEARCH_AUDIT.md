# Efficient On-Device Inference Research Audit

**Review date:** 2026-10-11  
**Repository:** `Porting-LLM-s-Model-Project`  
**Scope:** the React Native application, the checked-in benchmark harness, and a targeted literature review.

## 1. Executive result

The repository currently supports an offline RAG chat application, but it does
not yet contain publication-quality physical-device evidence. The 108-record
warm-query artifact was generated by a deterministic timing model in
`benchmark/run_benchmark.py`; it was not collected from an emulator or the
Redmi 12 5G. The old report therefore cannot be used to support a hardware
performance claim.

The first defensible optimization is now implemented as an opt-in,
per-request, evidence-preserving controller:

* `baseline` preserves the historical configuration: `n_ctx=512`,
  `n_threads=4`, `n_gpu_layers=0`.
* `fixed` selects an explicitly requested completion thread count.
* `adaptive` classifies document questions as single-hop, broad, or multi-hop;
  removes highly overlapping chunks; applies a whole-chunk context budget;
  chooses a bounded output budget; and explores configured thread candidates
  subject to current CPU, memory, and thermal state.
* Android telemetry is read through a small native module with conservative
  fallbacks. It records available processors, available memory, low-memory
  state, thermal status, battery temperature, and readable CPU frequencies.
* The controller records its decision and the native prompt/decode timings in
  `inference_benchmark_latest.json`.
* RAG retrieval now exposes embedding, vector-search, context-construction,
  selected-chunk, deduplicated context-size, and evidence-demand metrics. An
  explicit request can override the adaptive context/output budgets.

The normal chat path selects `adaptive` through
`DEFAULT_CHAT_INFERENCE_MODE`; changing that one constant to `baseline` keeps
the historical application behavior for a strict comparison.

This is an empirical systems contribution candidate, not a novelty claim. The
experiment must show whether it beats the best fixed thread count under
matched conditions before it is positioned as a paper contribution.

## 2. Repository and baseline audit

### 2.1 Actual application architecture

| Layer | Repository evidence |
|---|---|
| UI/runtime | React Native `0.78.1`, React `19.0.0`; `chat/package.json` |
| Native inference binding | `llama.rn` `0.5.8` in `chat/package-lock.json`; llama.cpp-backed native context |
| Main model | Downloaded at runtime from the catalog in `chat/screens/Models.tsx`; the recommended ID is `gemma-2-2b-it-Q4_K_M` |
| Embeddings | `all-minilm-l6-v2-q4_k_m`, `embedding: true`, 384-dimensional vectors |
| Retrieval | Word chunks of 100 words with 20-word overlap; in-memory per-profile cosine search; default top 3 |
| Prompt construction | `chat/tasks/qa.ts`; document mode injects retrieved context into a single user message |
| LLM context | Cached in `ChatScreen`; `n_ctx=512`, CPU-only, four threads |
| Native GPU/NPU | No verified Android offload in this repository; `n_gpu_layers=0` |
| Android build | arm64 and x86 variants are listed in `gradle.properties`; no checked-in model binary |

The initial prompt described batch and microbatch sizes of 512, but the actual
`initLlama` call did not pass `n_batch` or `n_ubatch`. They must be recorded as
runtime defaults until a device log confirms otherwise. The checked-in
`llama.rn` 0.5.8 types do expose native `prompt_n`, `prompt_ms`,
`predicted_n`, `predicted_ms`, per-second rates, token streaming callbacks, and
per-completion `n_threads`; the implementation uses those APIs.

### 2.2 Model metadata discrepancies to resolve on the phone

There is no GGUF binary in the repository, so the exact file size, SHA-256,
GGUF metadata, and native parameter count are not verified here. The app model
catalog says approximately 1.434 GB for `gemma-2-2b-it-Q4_K_M.gguf`, while the
synthetic benchmark configuration says 1,720 MB and “2.5 Billion” parameters.
Those are not interchangeable facts. Every physical run must include:

```bash
adb -s "$ANDROID_SERIAL" shell sha256sum \
  /sdcard/Android/data/com.chat/files/models/gemma-2-2b-it-Q4_K_M.gguf
adb -s "$ANDROID_SERIAL" shell dumpsys meminfo com.chat
adb -s "$ANDROID_SERIAL" shell getprop ro.product.model
adb -s "$ANDROID_SERIAL" shell getprop ro.build.version.release
```

The model hash and GGUF metadata should be copied into the run record before
comparing runs. A model downloaded from another URL or a different filename is
a different experimental condition.

### 2.3 Existing artifact reliability

`benchmark/results/warm_query_benchmark_results.json` contains 108 records
covering three named AVD profiles and three dataset sizes. In the original
runner, timings are computed from formulas such as:

```text
prefill = 1800 * (4 / configured_cores)
decode  = generated_tokens * 85 * (4 / configured_cores)
```

The records are useful for testing CSV/JSON/report generation, but not for
estimating a Pixel or Xiaomi device. They also omit model hash, actual prompt
token count, thermal state, battery state, and answer-quality labels. The
updated runner labels all newly generated synthetic records `SIMULATED` and
requires `--simulate` explicitly.

The old physical result path mentioned in the prompt,
`benchmark/results/physical_mobile_split_benchmark.json`, is absent from the
repository. No physical result was available to reproduce during this audit.

### 2.4 Measurement corrections implemented

The previous instrumentation treated `retrieval + native prompt_ms` as TTFT.
That is not TTFT. The current report distinguishes:

* `prefill_ms`: llama.cpp's native prompt-processing metric;
* `ttft_ms`: request submission through the first streamed token, including
  retrieval;
* `llm_ttft_ms`: completion start through the first streamed token;
* `decode_ms`: llama.cpp's native predicted-token timing;
* `total_warm_latency_ms`: request submission through completion.

If the runtime emits no token callback, TTFT is recorded as `null`, rather than
being substituted with prefill time. Profiling overhead from prompt
tokenization is recorded separately as `prompt_tokenization_ms`.

## 3. Target-device baseline procedure

The following is the minimum reproducible procedure for the Xiaomi Redmi 12
5G (`23076RN4BI`, Snapdragon 4 Gen 2, Android 15/HyperOS). The device must be
cool, charged, disconnected from unrelated workloads, and kept in the same
screen/power state for a trial block.

1. Build and install the same release APK for the whole experiment.
2. Download the exact chat and embedding GGUF files; record hashes.
3. Open the app, select the chat model, initialize the RAG index, and perform
   one warm-up query that is excluded from analysis.
4. Run a fixed query set with a fixed mode, output limit, temperature, model,
   context size, and thread count.
5. Execute at least 5 warm repetitions per workload, plus a separate cold-start
   block in which model-load time is measured before the first query.
6. Before and after each run, capture battery percentage, battery temperature,
   Android thermal status, all available CPU frequencies, and `dumpsys meminfo`
   PSS. Do not combine PSS, native heap, Java heap, mapped file size, and swap.
7. Save the JSON report, Logcat timing output, device metadata, and query/answer
   quality labels under a unique run ID.

Example physical run:

```bash
cd benchmark
python run_device_inference.py \
  --serial "$ANDROID_SERIAL" \
   --query "Tell me about zypher" \
   --mode document \
   --inference-mode baseline \
   --rag-policy ebmrag-v2 \
   --model-path /sdcard/Android/data/com.chat/files/models/gemma-2-2b-it-Q4_K_M.gguf
```

The controller experiment uses the same trigger with
`--inference-mode adaptive`. To isolate a thread candidate, use
`--inference-mode fixed --threads 2`, then repeat for 4, 6, and 8. The first
controlled sweep should use a fixed context and output budget; only afterward
should thread adaptation be combined with context-budget adaptation.

For the evidence-contract comparison, repeat the same query block with
`--rag-policy mobcert-v1`. The device report records the requested policy and
the returned `answerContract`; do not combine those records with synthetic
benchmark output. Each physical report is written to a unique file under
`benchmark/results/physical_runs/`. Aggregate matched labeled runs with
`python3 benchmark/evaluate_physical_runs.py` before calculating policy-level
medians and quality trade-offs.

The review was checked against accessible arXiv records and the installed
runtime documentation on 2026-10-11. Numerical results below are claims made
by the cited papers, not results from this repository.

### 4.2 Runtime and hardware evidence

* The checked-in `llama.rn` 0.5.8 README documents CPU Android support and the
  completion callback/timing API, but its Android note says that the 0.5.8
  branch has no integrated GPU backend. Its current upstream README describes
  OpenCL and experimental Hexagon support, with tested-device/data-type
  restrictions that must not be projected onto this pinned version.
* The official [llama.cpp Android documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md)
  documents Android cross-compilation and warns that context size affects
  memory. It does not establish that the app's prebuilt `llama.rn` native
  artifact has an enabled Adreno or Hexagon path.
* Android's `PowerManager` thermal status API can provide a thermal signal, but
  a thermal status and a CPU-frequency drop are separate observations. The
  physical script therefore stores both when available and does not label a
  run throttled from temperature alone.

## 5. Candidate research directions and ranking

| Rank | Candidate | Novelty after review | Feasibility | Main invalidation test |
|---:|---|---|---|---|
| 1 | Measurement-driven per-query thread policy for one pinned llama.rn model on a low-cost phone | Moderate at most; related schedulers and adaptive inference already exist. The defensible contribution would be a reproducible phone/RAG study with an interpretable policy, not “first adaptive inference.” | High: `llama.rn` exposes per-completion `n_threads`; no model conversion required. | The best fixed thread count is no slower than adaptive mode, or adaptation overhead/variance dominates. |
| 2 | Retrieval-aware whole-chunk context budget with answer-grounded quality labels | Low-to-moderate; adaptive retrieval and context compression are established. Value would be the controlled mobile latency/quality Pareto curve. | High: current RAG pipeline already owns top-K selection. | A smaller context loses evidence or does not reduce native prefill. |
| 3 | CPU versus Android GPU/NPU backend comparison | Potentially useful empirical study, but no algorithmic novelty. | Uncertain: pinned llama.rn 0.5.8 and target Adreno 613/Hexagon capability are unverified; model/operator/quantization support may fail. | Offload is unavailable, slower, unstable, or consumes too much memory. |
| 4 | Thermal-aware adaptation | Low novelty as a generic idea; could become a careful sustained-use study. | Medium: thermal status and frequencies are observable, but reliable energy attribution is difficult. | No repeatable latency/frequency/thermal relationship appears, or controller cannot improve sustained service. |
| 5 | Mamba/RetNet replacement | Architecture research rather than an incremental app optimization. | Low for this codebase: new checkpoint format, runtime, and quality baseline are required. | No deployable checkpoint/runtime or no quality-matched gain. |

## 6. Recommended research question and hypothesis

**Research question:** On the Redmi 12 5G, can an evidence-preserving,
resource-aware per-query policy reduce warm RAG latency relative to a fixed
configuration by allocating only the context and output budget required by the
question, while preserving answer quality and avoiding unacceptable sustained
run degradation?

**Hypothesis:** Single-hop document questions do not require all top-ranked,
overlapping chunks, and the best thread count depends on prompt-size bucket
and device state. A policy using evidence demand, exact prompt-token count,
recent native prefill/decode timings, and current thermal/memory signals will
reduce median warm latency or improve the latency tail under a fixed quality
constraint. This hypothesis is unconfirmed.

**Implementation now in the repository:** `inferenceController.ts` performs
interpretable evidence-demand classification and exploration/exploitation by
workload bucket. `ragPipeline.ts` removes near-duplicate overlapping chunks
and applies a whole-chunk budget. `DeviceTelemetryModule.kt` supplies current
resource signals. `qa.ts` records the selected policy, reason, native timings,
first-token timing, device state, and RAG-stage metrics. The default app path
remains baseline. The physical trigger can run baseline, fixed, or adaptive
requests without rebuilding the APK.

The current RAG implementation is now a separate end-to-end artifact:
`chunker.ts`/`evidenceSelector.ts` implement structure-aware, extractive
Evidence-Budgeted Mobile RAG v2; `vectorStore.ts` provides bounded hybrid
retrieval with atomic persistence; `promptBudget.ts` counts the actual chat
template and reserves output tokens; and `metrics.ts` refuses to fabricate
correctness or groundedness without labels. The algorithm is an engineering
policy built from established hybrid retrieval and compression ideas, not a
new general RAG theorem.

The opt-in `mobcert-v1` path is documented separately in
`research/MOBCERT_CONTRACT_RESEARCH.md`. Its contract review now covers
attribute-scoped numeric and qualitative values, local polarity, table-row
column semantics, enumeration, partial evidence, citation auditing, and
contradictory-source status. The contract is regression-tested in the
production-module suite, but it has no physical-device result claim yet.

The computer-side benchmark utilities were also repaired and checked: the
master wrapper now uses the active Python interpreter, vector inspection no
longer requires undeclared NumPy, and the offline evaluator has explicit
content-token precision plus numeric-token groundedness tests. The generated
108-record timing artifact remains `SIMULATED` and is suitable only for
validating report generation, not for a hardware result section.

## 7. Controlled experiment matrix

Run each cell with identical model hash, prompt set, output limit, temperature,
document index, screen/power state, and warm-up policy. Report median, IQR,
standard deviation, and bootstrap 95% confidence intervals; use paired tests
over the same query/run order where appropriate.

| Experiment | Independent variable | Controls | Required evidence |
|---|---|---|---|
| Prompt scaling | 64/128/256/384/512 native prompt tokens | fixed 4 threads, same output budget | prompt_n, prefill_ms, prefill tok/s |
| Thread sweep | 1/2/4/6/8 completion threads | fixed prompt/output/model; cool device | TTFT, prefill, decode, total, frequency |
| Retrieval budget | top-K or whole-chunk context budget | fixed threads and answer set | selected chunks, prompt_n, Recall@K/evidence coverage, answer correctness |
| Output scaling | 16/32/64/128 generated-token limit | fixed prompt and thread count | generated tokens, decode ms, tokens/s |
| Sustained run | repeated blocks over time | same fixed setting, cooldown block | temperature, thermal status, frequencies, latency trend |
| Adaptive policy | baseline, best fixed, adaptive | same randomized query sequence | paired latency/quality/memory comparison; controller overhead |

The controller fails the primary hypothesis if adaptive median latency is not
better than the best fixed setting within the prespecified tolerance, if its
95th percentile worsens materially, or if answer quality/evidence coverage
drops beyond the accepted margin. A negative result is publishable only as a
careful empirical systems study with enough matched runs and explicit scope.

## 8. Quality protocol

The profiler deliberately records `quality_evaluation: not_measured`; it never
turns a generated answer into a quality claim. Build a separate labeled set
with factual single-chunk questions, multi-chunk synthesis questions,
insufficient-evidence questions, and irrelevant-context distractors. Annotate:

* retrieval Recall@K and evidence coverage;
* answer correctness and groundedness against an answer key;
* refusal correctness when evidence is insufficient;
* task success for the same fixed prompts.

Compare every latency configuration against the same baseline answers. Do not
report a faster answer that used less context without its quality trade-off.

## 9. Paper-readiness status

The repository is ready for the experiment implementation and physical data
collection. It is not ready for an IEEE results section: there is no verified
Redmi measurement set, no confidence interval, no model hash in a physical
record, no quality-labeled dataset, and no backend comparison. Until those
artifacts exist, use “candidate contribution” and “hypothesis,” not “novel” or
“state of the art.”

The first physical batch is now explicitly audited in
`research/PHYSICAL_RUN_AUDIT.md`. It contains genuine device records, but
query/policy mismatches and stale fixed-top-k EBM labels prevent it from being
used as the final matched comparison. The collector and evaluator now reject
these inconsistencies and report skipped-inference quality as N/A.

If the controller wins, the paper can be positioned as a reproducible mobile
systems evaluation plus a small online policy. If it does not win, the strongest
outcome is a negative result identifying the best fixed configuration and the
limits of adaptive scheduling on this device.
